Three ways to achieve full feature parity

All three include Notchi chat/agents and all Boring Notch features. The difference is where the product boundary lives.

Notchi app + UI
↓
Ported Boring services
adapters · one state model

A. Native integration — recommended

Keep one Notchi application, port Boring’s services and models into feature modules, and rebuild every visible surface in the Notchi design system.

Combined source target
↕
Notchi + Boring views
shared globals & dependencies

B. Literal source merge

Copy the Boring project almost wholesale into the root target and replace or suppress its UI. Fastest initial transplant; highest collision and maintenance risk.

Notchi app
⇄ IPC
Boring helper app
separate lifecycle

C. Sidecar integration

Keep Boring as a helper process and surface its state in Notchi. Least intrusive initially, but violates the single-app product goal and complicates installation.

Why A is the fit

  • One app and one make run
  • Notchi stays visually and behaviorally coherent
  • Boring features become agent-callable capabilities

Cost

  • It is a real port, not a blind copy
  • Private/XPC code needs isolated optional modules
  • Full parity should be delivered in phases
